For maintainers. How to add a call to `H3SpatialService`, and how the module is tested on every target.

## Adding a function

Every target already has Uber's full H3 API available: `com.uber:h3` on the JVM and Android, the whole of `h3api.h` through cinterop on iOS, and `h3-js` on the web. Adding a function needs no native rebuild:

1. Add it to [`H3SpatialService`](../../../h3spatial/src/commonMain/kotlin/com/oddlyclever/h3spatial/H3SpatialService.kt), with its validation, and to the internal [`H3Native`](../../../h3spatial/src/commonMain/kotlin/com/oddlyclever/h3spatial/H3Native.kt) seam.
2. Implement `H3Native` for each target: a `com.uber:h3` call on the JVM and Android, a cinterop call on iOS, and for JS and wasmJs an external declaration in `h3js/H3Js.kt`, written from `h3-js`'s own typings, plus the call.
3. Annotate it `@Throws(H3SpatialException::class)` if it can fail.
4. Add it to `H3SpatialServiceSpec`, and to `UberAgreementSpec` if H3's test data covers it.

Validation belongs in the service, in shared code, not in each `H3Native`. Some `h3-js` functions return sentinel values instead of throwing on invalid input, and each platform rejects a different set of bad inputs, so only shared validation makes every target refuse the same inputs with the same code. Where a result is sized from the input, bound it in the service too, as `gridDisk` bounds `k` and `cellToChildren` bounds the resolution step: the iOS binding sizes its output buffers from those values.

Functions returning H3's linked structures take more care on iOS, where the C API hands back memory the caller must free. `cellsToLinkedMultiPolygon`, for instance, returns a `LinkedGeoPolygon` that must be walked and then released with `destroyLinkedMultiPolygon`; `com.uber:h3` and `h3-js` return ordinary collections for the same call.

The JVM and Android implementations are near copies, differing only in how the native library is loaded. Sharing them would need a custom JVM-plus-Android source set, which costs more than a short file.

## Verification

Two suites run on every target, each from a per-target test class, because every platform binds H3 by a different route and only a run on that platform proves its binding. They are plain objects in `commonTest`, called from `JvmH3SpatialServiceTest`, `IosH3SpatialServiceTest`, `JsH3SpatialServiceTest`, `WasmJsH3SpatialServiceTest` and `AndroidH3SpatialServiceTest`, rather than common `@Test`s; a common `@Test` would also run as an Android host unit test, where the native library cannot load.

- **`H3SpatialServiceSpec`** pins the service's own contract: canonical indexes, geometry, traversal, pentagons, hierarchy, GeoJSON and the failure contract, including error codes.
- **`UberAgreementSpec`** is the drift guard. It checks the service against Uber's own reference data for the vendored release: 1,468 points that must fall in their recorded cells, 892 cell boundaries including every resolution-0 cell and so every resolution-0 pentagon, and 964 cell centres. A wrong binding, a mismatched native build or a transposed coordinate fails here, on the platform where it happens. It also checks that the data is there, so it cannot pass vacuously.

The reference data is in `src/commonTest/kotlin/UberH3Fixtures.kt`, generated by [`native/generate-agreement-fixtures.py`](../../../h3spatial/native/generate-agreement-fixtures.py) from H3's `tests/inputfiles` at the vendored tag. `update-source.sh` regenerates it, so the expected values always match the vendored H3. It is embedded in Kotlin source because the tests cannot read files on JS, wasmJs or iOS. Never edit it by hand.

Both suites pass on `jvmTest`, `jsBrowserTest`, `wasmJsBrowserTest` and `iosSimulatorArm64Test`, which `./gradlew :h3spatial:check` runs.

Android cannot load its native library in a host test, so the module has no Android host test, although `commonTest` exists and the Android Gradle plugin warns about it. Its suite lives in `androidDeviceTest` and runs with `./gradlew :h3spatial:connectedAndroidDeviceTest` against an ARM device or emulator. It has been run on an Android 16-era arm64 emulator with 16 KB memory pages, and on an API 24 arm64 emulator.
