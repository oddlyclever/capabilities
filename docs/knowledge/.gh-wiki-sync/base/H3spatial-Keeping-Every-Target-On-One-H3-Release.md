# Keeping Every Target on One H3 Release

DOC-0007 · 2026-11-04
Keywords: H3 version, upgrade H3, H3 4.5.1, H3 master, h3-java release, com.uber:h3 4.5.1, h3-js version, uberH3, h3Js, native/PROVENANCE, h3lib/VERSION, update-source.sh, build-natives.sh, re-vendor H3, rebuild libh3.a, cmake not found, h3api.h stale header, h3api.h committed, cinterop commonization, compare symbols not bytes, different answers per platform, vertex mode, cellsToLinkedMultiPolygon, _baseCellToCCWrot60 out-of-bounds read

For maintainers. Every target runs the same H3 release, currently H3 4.5.0. This page is where that version is recorded, why the module is held at 4.5.0, and how to move it.

## Where the version is pinned

The version is asserted in several places, and they must agree:

- [`native/PROVENANCE`](https://github.com/oddlyclever/capabilities/blob/HEAD/h3spatial/native/PROVENANCE): the tag and commit the H3 C source was vendored from, and the h3-java release the JVM and Android artifacts must be. It is authoritative, and regenerated by script, never edited by hand.
- [`native/h3lib/VERSION`](https://github.com/oddlyclever/capabilities/blob/HEAD/h3spatial/native/h3lib/VERSION): copied verbatim from the upstream tree.
- `uberH3` in [`gradle/libs.versions.toml`](https://github.com/oddlyclever/capabilities/blob/HEAD/gradle/libs.versions.toml): `com.uber:h3` for the JVM and `com.uber:h3-android` for Android, which h3-java releases together. It must be the h3-java release named in `native/PROVENANCE`.
- `h3Js` in the same catalog: the npm package for JS and wasmJs.

These move together or not at all. A version that advances on some targets and not others gives different answers per platform for the same input, which is the failure the whole arrangement exists to prevent. The agreement tests catch it if they drift; see [Adding a Function and Verifying It](H3spatial-Adding-A-Function-And-Verifying-It).

## Waiting on 4.5.1

The module is held at 4.5.0 on purpose, even though upstream `master` has moved ahead of the tag.

There is no 4.5.1 tag of H3, and the matching `h3-js` changes are unreleased on npm. `com.uber:h3` has a 4.5.1, but it is the same binding on H3 4.5.0, re-released to sign with a new key, so it changes nothing this library runs. Only the vendored C could follow `master`, and doing so would put iOS ahead of every other target and replace a reproducible tag pin with a moving branch reference. Neither is worth it: nothing in the current `master` delta is reachable from this library's surface.

When H3 4.5.1 ships, move once `com.uber:h3` and `h3-js` have released against it too. That release is expected to carry the fix for an out-of-bounds read in `_baseCellToCCWrot60` when passed a face index equal to `NUM_ICOSA_FACES` ([uber/h3#978](https://github.com/uber/h3/issues/978), fixed by [uber/h3#1224](https://github.com/uber/h3/pull/1224)). The affected path is reached only from H3's vertex API, which this library does not expose.

Vertex-mode bindings are a candidate follow-on at that point, not before. Drawing merged cells, a set of cells rendered as one outline rather than one ring per cell, does not need vertex mode; that is easy to assume otherwise. It needs `cellsToLinkedMultiPolygon`, which is already public in 4.5.0 and does not route through the vertex code at all. Vertex mode is a separate capability, useful for treating shared corners as first-class identities: integer equality on a corner shared by three cells, and consistent coordinates whichever cell it is approached from.

## The vendored C source

The H3 C library is vendored, unmodified, under [`native/h3lib`](https://github.com/oddlyclever/capabilities/blob/HEAD/h3spatial/native/h3lib), and the iOS static libraries built from it are committed, so consumers need no CMake and no network access to an upstream checkout. Only iOS compiles it: the JVM and Android use Uber's published artifacts, and the web uses `h3-js`.

Updating takes two scripts, run in order and committed together, from the repository root:

```bash
./h3spatial/native/update-source.sh v4.5.1 v4.5.1
```

```bash
./h3spatial/native/build-natives.sh
```

[`update-source.sh <h3-tag> <h3-java-tag>`](https://github.com/oddlyclever/capabilities/blob/HEAD/h3spatial/native/update-source.sh) re-vendors the C source, regenerates the agreement test fixtures from H3's test data at the same tag, and rewrites `native/PROVENANCE`. It also checks that the given h3-java release was built against that H3 tag, from h3-java's `h3version.properties`, and refuses to continue otherwise. That release is what `com.uber:h3` and `com.uber:h3-android` must be, so the check keeps iOS on the same H3 as the JVM and Android. It needs `git` and `python3`. Never hand-edit anything it writes: it replaces each file wholesale, so a local edit is silently lost on the next update.

[`build-natives.sh`](https://github.com/oddlyclever/capabilities/blob/HEAD/h3spatial/native/build-natives.sh) rebuilds both committed `libh3.a` files, for `iosArm64` and `iosSimulatorArm64`, plus the generated cinterop header. It builds for iOS 14.0 and later. It finds CMake itself, from the `CMAKE` environment variable, the newest CMake in the Android SDK, or the `PATH`, in that order, and fails with "cmake not found" if there is none. It builds from clean every time.

The header and the library must come from the same version: a stale header against a newer library compiles cleanly and fails at runtime. So the header is copied from the build rather than kept by hand, and `native/h3lib/include/h3api.h`, which CMake generates from `h3api.h.in`, is git-ignored; a committed copy of it is how this module once lost track of its own H3 version.

After updating, set `uberH3` and `h3Js` in the version catalog to the same release, and run the checks in [Adding a Function and Verifying It](H3spatial-Adding-A-Function-And-Verifying-It).

When checking a rebuild against what is committed, compare exported symbols, not bytes. Different toolchain generations produce byte-different binaries from identical source; a symbol difference is the signal that matters.

## Cinterop commonization

The repository's `gradle.properties` enables cinterop commonization (`kotlin.mpp.enableCInteropCommonization=true`). The shared iOS source set imports the cinterop `h3` package, and without commonization the metadata compilation that publishing needs cannot see that package.
